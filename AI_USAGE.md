# AI_USAGE.md

## Что делалось с AI

Весь код написан AI-агентом в две сессии на основе OpenAPI-схемы и текста задания.

**Сессия 1 (базовая реализация):** структура FSD, роутинг TanStack Router, MSW-моки с in-memory стором,
формы RHF+Zod, компоненты списка/детали/ставки на инлайн-стилях, юнит-тесты.

**Сессия 2 (редизайн и доводка до требований задания, этот проход):** по запросу кандидата — полный
визуальный редизайн на Tailwind CSS (дизайн-система: цвета, тени, радиусы, типографика, состояния),
переработка адаптива (мобильный bottom-sheet для фильтров, отзывчивые сетки), добавление недостающего
обязательного фильтра «статус аукциона», а также поиск и исправление багов, найденных при сборке и
end-to-end проверке через headless-браузер (Playwright-скрипты, не включены в репозиторий).

## Решения, принятые самостоятельно (кандидатом, как постановщиком задачи AI)

- Роутинг сделан code-based (`createRoute` в одном `router.tsx`), а не файловым генератором TanStack Router —
  code-based даёт тот же публичный API и типобезопасность без отдельного build-шага генерации.
- Bet-форма — отдельный **route** (`/auctions/$id/bet`), а не модалка поверх детальной страницы: задание
  требует «режим установки ставки должен открываться по ссылке», отдельный URL это гарантирует однозначно.
- Фильтры синхронизированы в URL search params, а не в localStorage — ссылка на отфильтрованный список
  аукционов шарибл и переживает перезагрузку без скрытого состояния.
- Готовая UI-библиотека не подключалась — вместо неё выбран Tailwind CSS: он даёт полный контроль над
  дизайн-системой (палитра/тени/радиусы как токены в `tailwind.config.js`), держит бандл компактным и
  оставляет весь визуальный код читаемым в ревью (в отличие от закрытых компонентов сторонних либ).
  Специализированного «дизайнерского» skill/пресета для этого репозитория не было — дизайн-система
  (цвета статусов, карточки, bottom-sheet, тосты, иконки) спроектирована и сведена вручную в рамках сессии.
- Мобильный UI: вместо того чтобы просто «сжимать» десктопную раскладку, для фильтров сделан отдельный
  сценарий — bottom-sheet с теми же полями через общий `FiltersForm`, чтобы на маленьком экране форма
  фильтров не превращалась в длинный список без визуальной группировки.
- Тип аукциона / статус аукциона / мой торговый статус в фильтрах реализованы как toggle-чипы (а не
  `<select>` с одним значением), потому что OpenAPI-схема явно описывает эти поля как массивы
  (`auc_type: string[]`, `statuses: number[]`, `status: string[]`) — чипы честно поддерживают multi-select,
  чего не было в первой версии (там были одиночные `<select>`, фактически ограничивавшие фильтр одним
  значением при том, что API принимает массив).
- Zustand ограничен точечным client-state (тосты с авто-скрытием, состояние мобильного drawer фильтров) —
  весь серверный стейт живёт в TanStack Query, как и требовало задание.

## AI-предложения, которые были отклонены

- Черновой вариант редизайна предлагал подключить полноценную UI-кит библиотеку (например, headless UI +
  готовые стили) — отклонено в пользу собственного набора примитивов на Tailwind, чтобы вся логика состояний
  (disabled/invalid/loading) оставалась прозрачной и не зависела от API конкретной библиотеки.
- Предлагалось хранить открытое/закрытое состояние мобильного bottom-sheet фильтров в URL (`?filtersOpen=1`) —
  отклонено: это чисто клиентское UI-состояние, не влияющее на данные и не нужное для шаринга ссылки, поэтому
  для него достаточно уже существующего Zustand-стора (`filtersDrawerOpen`), как и требовало задание
  («MobX или Zustand для точечного клиентского UI-state»).
- Предлагалось скрыть карточки статуса аукциона за один общий бейдж «статус» — отклонено, так как задание
  явно требует отдельно показывать и статус аукциона, и торговый статус пользователя (это разные сущности
  по схеме: `AuctionStatus` и `TradingStatus`), их слияние запутало бы проверяющего.

## Что проверялось особенно внимательно

- Соответствие enum-значений схеме (`AuctionType`, `AuctionStatus`, `TradingStatus`, `BidMeasurementType`) —
  сверено построчно с `openapi.auctions.v0.json`, никаких «придуманных» значений; добавленный фильтр по
  `statuses` (числовой статус аукциона) сверен с маппингом `AUCTION_STATUS_NUMERIC`.
- Обработка nullable-полей детальной карточки (`trading.price.min/max/step`, `cargo.car`, `payment.delay`) —
  везде явные проверки на `null`/`undefined`, а не оптимистичное приведение типов.
- 422-ошибка установки ставки: сервер (MSW) — единственный источник истины по `errors[]`, клиентская Zod-
  валидация дублирует те же правила (min/max/step), но не «глотает» серверный ответ.
- Инвалидация React Query после успешной ставки: проверено через полный клиентский флоу (без перезагрузки
  страницы) — статус пользователя, текущая цена, бейдж «моя ставка» и список ставок обновляются на всех
  экранах (список, детальная, ставки) сразу после мутации.
- При визуальном ревью через headless-браузер обнаружено и исправлено: (1) неверный путь импорта в
  `mappers.ts`, скрытый тем, что `import type` не резолвится в рантайме и не ловится юнит-тестами; (2)
  несколько `<Link>` без обязательных search-параметров, из-за чего `tsc -b` (строгий build) падал, хотя
  `vite dev` в рантайме этого не показывал; (3) рассинхронизация `min`/`step` в генераторе моков, из-за
  которой автоподставленное в форму значение цены не проходило собственную же step-валидацию.

## Риски, которые остались

- MSW-фильтрация в `handlers.ts` реализована только для обязательного минимального набора полей — остальные
  поля `AuctionListRequest` из схемы принимаются, но игнорируются мок-сервером.
- Генератор мок-данных (`mocks/db.ts`) не покрывает все комбинации статусов/флагов равномерно (вероятностный),
  поэтому конкретный edge case может не встретиться без повторной перезагрузки — сид фиксирован, но
  распределение не гарантирует 100% покрытие всех веток UI при одном запуске.
- Ранжирование ставок (`place`) в моках после отправки новой ставки пересчитывается по порядку в массиве
  (лучшая — первая), а не по реальному сравнению цен с учётом направления торгов (`Up`/`Down`/`FixPrice`) —
  для реального бэкенда это было бы бизнес-правилом сервера, здесь это упрощение мок-слоя.
- Нет интеграционных/e2e-тестов в самом репозитории (только юнит-тесты на чистую логику: search-params
  parsing, request builder, ViewModel-мапперы, validation schema ставки) — полный пользовательский сценарий
  в этой сессии проверялся вручную через временные Playwright-скрипты (список → фильтры → детальная →
  ставка → инвалидация), которые не были оставлены в кодовой базе.
- `formatMoney`/`formatNumber` используют `Intl.NumberFormat('ru-RU')` без отдельного money-value-object —
  для реальной денежной точности (округления НДС и т.п.) в проде стоило бы вынести это в отдельный модуль.

## Что кандидат улучшил бы при наличии ещё одного дня

- Добавить Playwright/Testing Library интеграционные тесты поверх MSW-хендлеров как часть репозитория (сейчас
  такая проверка была сделана вручную, но не оформлена как автоматический тест-сьют).
- Вынести мок-фильтрацию и ранжирование ставок в отдельные переиспользуемые модули с полным покрытием всех
  полей `AuctionListRequest` и корректным учётом направления торгов при пересчёте `place`.
- Добавить виртуализацию списка аукционов для больших `per_page` и debounce на текстовые поля фильтров.
- Проработать доступность подробнее: фокус-менеджмент при открытии bottom-sheet и переходе на страницу ставки,
  aria-live для тостов, более полный набор aria-атрибутов для чипов-фильтров.
- Добавить тёмную тему (дизайн-токены Tailwind уже подготовлены как палитра, добавление `dark:`-вариантов —
  относительно небольшая доработка поверх текущей дизайн-системы).
